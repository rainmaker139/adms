## 분석 결론과 현행 근거

현재 앱은 오프라인 단일 HTML 빌드 검증용 골격이다. 업무 프로토타입이 이미 구현되어 있다고 볼 수 없다. 기술 기반은 활용할 수 있으나 PRD의 업무 도메인과 역할별 IA는 대부분 신규 설계·구현 대상이다. 업무화면을 그대로 유지할 수 있는 사례는 없다.

| 확인 파일 | 실제 구현 | 평가의 근거 |
|---|---|---|
| `src/App.tsx` | HashRouter, `/dashboard`, `/markets`, `/operations`; 루트/미지 경로는 Dashboard로 이동 | Role·사업·조직·점포 구분 및 권한 가드 없음 |
| `src/layouts/DemoLayout.tsx` | Dashboard/참여마트/농할운영의 고정 1단 메뉴, Lucide 아이콘, Outlet | 현재 IA의 전부이며 역할별 메뉴가 아님 |
| `src/pages/Dashboard.tsx` | KPI 3개와 월별 막대차트 1개 | 업무 데이터 집계나 상세 이동 없음 |
| `src/pages/TestPage.tsx` | 두 경로가 같은 컴포넌트를 사용; 제목과 로컬 카운터만 다름 | 참여마트 목록·농할 기능·상세 화면은 존재하지 않음 |
| `src/components/KpiCard.tsx` | label/value를 표시하는 카드 | 순수 표시 컴포넌트로 재사용 가능 |
| `src/data/demo.ts` | 참여마트 12개, 행사 3개, 집행액 450만원; 1~4월 차트값 40/65/50/90 | 관계 없는 고정값이며 PRD 표준 시나리오와 연결되지 않음 |
| `src/types/demo.ts` | `Kpi`, `ChartPoint`만 존재 | 사업·조직·회원사·점포·정산 등 도메인 타입 없음 |
| `src/main.tsx`, `src/index.css`, `index.html` | React 진입점, Tailwind, 시스템 폰트, inline favicon | 오프라인 프런트엔드 기반 재사용 가능 |
| `vite.config.ts`, `package.json` | React/TS/Vite, 일반 빌드 및 singlefile 플러그인, HTML 이름 변경, public 복사 차단 | 단일 HTML 산출 요구에 맞는 기반 |
| `scripts/verify-single.mjs` | 산출 파일 수, HTML/CSS 참조, 정적 모듈 참조 검사 | 업무 구현 후에도 유지·확장할 품질 게이트 |
| `scripts/smoke-offline.mjs` | Edge file://, 네트워크 offline, localStorage 차단, 기존 세 화면 검증 | 현재 검증용 화면에 종속되어 있어 IA 개편 시 수정 필요 |

이하 표의 **PRD 요구**는 준수 대상이다. **구현 제안**은 해당 요구를 표현하기 위한 프런트엔드 설계안이며, PRD가 미정으로 남긴 기관 정책이나 인터페이스 규격을 확정하지 않는다.

## 1. 현재 구현된 IA와 PRD Target IA 차이

### 1.1 현재 IA의 한계

| 현재 경로/메뉴 | 현재 내용 | PRD 기준 차이 | 전환 방향 |
|---|---|---|---|
| `#/dashboard` / Dashboard | 모든 사용자에게 동일 KPI/차트 | PRD 7.1, 8.1, 9, 10.2, 11.1은 역할·범위·처리할 일에 따른 홈 요구 | 역할별 홈의 데이터 및 카드 구성으로 재설계 |
| `#/markets` / 참여마트 | 테스트 카운터 | 회원사, 점포, 가입심사, 사업 참여, 관리계정, POS 연동을 표현하지 않음 | 회원·조직 관리와 점포 운영, 사업 참여를 서로 다른 업무로 분리 |
| `#/operations` / 농할운영 | 테스트 카운터 | 예산→주차계획→상품등록→집행→청구→불인정→최종정산→지급 전체 없음 | 단계별 목록/상세/액션 및 공통 데이터를 신규 구성 |
| 고정 메뉴 3개 | 사용자/사업 컨텍스트 없음 | PRD 4, 5, 7.4~7.6의 메뉴·액션·범위 조합 미구현 | 프로그램 마스터, 사업 매핑, Role 권한으로 메뉴 생성 |

`참여마트` 하나를 회원사·점포·사업참여의 통합 객체로 확대하지 않는다. PRD의 회원사≠점포, 사업≠조직 원칙을 먼저 적용한다. 기존 경로 보존은 요구사항이 아니며, 후속 구현에서 경로가 바뀌면 필요에 따라 명시적 이동 안내만 제공한다.

아래 메뉴는 PRD 5장의 범위다. 현재 세 테스트 화면을 제외한 업무 영역은 모두 미구현이며, 같은 업무의 역할별 뷰는 공통 상세를 재사용한다.

**계층의 차이:** 현재는 단일 1단 메뉴지만 Target은 역할별 그룹→업무 목록→공통 상세→하위 품목/거래의 구조다. 사업·조직·점포 컨텍스트와 행사 주차/정산 차수 필터가 메뉴와 함께 유지되어야 한다. 필터가 권한 밖의 데이터를 조회하도록 범위를 넓혀서는 안 된다.

## 2. 그대로 유지 가능한 기존 화면과 공통 컴포넌트

### 2.1 그대로 유지할 수 있는 범위

| 대상 | 유지 여부 | 사용 조건 |
|---|---|---|
| 완성된 업무 화면 | 없음 | 세 경로 모두 업무 기능이 없는 검증 화면 |
| `KpiCard`의 label/value 표시 | 그대로 재사용 가능 | 단순 표시 카드로 사용. 클릭 이동/단위/상태가 필요한 홈 카드는 합성 또는 확장 |
| HashRouter + Outlet 기반 탐색 | 방식 유지 | 경로 정의·가드·메뉴 데이터는 교체 |
| React 진입점/TypeScript 설정 | 유지 | PRD 적용을 위해 프레임워크 교체 불필요 |
| Tailwind/시스템 폰트/Lucide | 유지 | 아이콘은 inline SVG, 자산은 번들 내부만 사용 |
| Recharts | 라이브러리 유지 | 현재 차트의 데이터·지표 정의는 대체; 권한 범위 집계로 구성 |
| `src/pages/components/layouts/data/types/assets` 역할 분리 | 유지 | 도메인별 하위 폴더로 확장 |
| `npm run dev`, `build`, `build:single`, singlefile 설정 | 유지 | 최종 산출물은 여전히 `dist/adms-demo.html` 하나 |

레이아웃의 flex 구조, 메뉴 활성 표시, 카드 테두리, 차트 컨테이너는 시각적 출발점으로 사용할 수 있다. 이 사실이 현재 메뉴명·업무 분류·KPI를 보존해야 한다는 뜻은 아니다. 테이블/필터/상세 패널/업로드/승인 모달 등은 현재 공통 컴포넌트로 존재하지 않는다.

## 3. 수정이 필요한 화면

현재 화면 중 '기존 업무 로직에 소폭 수정을 가하는 화면'은 없다. 다음은 기술적 틀을 재사용하면서 내용을 크게 수정할 대상이다.

| 대상 | 수정 범위 | PRD 근거 |
|---|---|---|
| Dashboard의 홈 틀 | 역할별 KPI, 금주/차주/마감, 처리 필요 카드, 관련 화면 이동, 범위별 집계 | 7.1, 8.1, 10.2, 11.1, 17.1 |
| DemoLayout의 앱 틀 | 역할별 다단 메뉴, 조직·사업·권한점포 컨텍스트, 조직별 공지/브랜딩, 참여사업에 따른 노출 | 4, 5, 7.2, 7.4~7.6 |
| KPI/차트 표시 연결부 | 독립 고정값 대신 동일 업무 데이터에서 집계; 집계와 상세 필터 일치 | 8.15, 19 |
| 기존 검증 시나리오 | 고정 3메뉴/카운터 검증을 역할·업무·권한·오프라인 검증으로 확장 | AGENTS, 17, 부록 C |

홈은 명칭 변경으로 끝내지 않는다. 예를 들어 협회는 금주 예산/집행률/진행점포와 심사·회비, 마트는 차주 상품등록/가입승인/불인정, 시스템 관리자는 POS·자동작업·감사, AT는 감독·검토 대기를 우선한다. 지회 홈의 세부 KPI는 PRD에 열거되지 않았으므로 자기 지회 범위에서 상세기획한다.

## 4. 폐기 또는 전면 재설계가 필요한 화면

| 대상 | 판단 | 이유 및 대체 |
|---|---|---|
| `TestPage`를 사용하는 참여마트 화면 | 업무 화면으로 폐기 | 카운터와 설명뿐이다. 회원사 목록/상세, 점포 운영, 가입·사업참여 심사로 새로 설계 |
| `TestPage`를 사용하는 농할운영 화면 | 업무 화면으로 폐기 | 농할의 어느 단계도 표현하지 않는다. PRD 8~11장의 단계별 공통 업무로 대체 |
| 현재 Dashboard의 정보 구성 | 전면 재설계 | 12개/3개/450만원과 1~4월 차트는 PRD 샘플/컨텍스트와 무관 |
| 고정 3개 메뉴 배열 | 전면 재설계 | Role, 사업-프로그램, 조직 예외권한, 점포 참여상태를 반영할 수 없음 |
| `demo.ts`의 KPI 중심 데이터 모델 | 도메인 기준으로 교체 | 표시값으로 업무 객체·원장·스냅샷·권한을 역산할 수 없음 |

카운터를 유지해야 한다면 개발 검증 전용으로만 격리할 수 있으나 Target IA에 포함할 필요는 없다. 이번 단계에서는 어떤 파일도 삭제하거나 화면을 변경하지 않는다.

## 5. 신규 생성이 필요한 화면

다음은 **화면군 단위 구현 목록**이다. 각 행은 별도의 TSX 파일 하나를 뜻하지 않는다. 목록/상세/탭/모달 구분은 후속 화면 설계에서 정하고, 같은 객체의 상세는 역할 간 공유한다. 모든 화면은 PRD 19.1의 목적, Role/범위, KPI/마감, 필터, 리스트/상세, 액션, 검증, 상태, 연동분기, 이력을 정의해야 한다.

### 5.1 플랫폼 공통 및 시스템 관리

### 6.3 HUB·공개·횡단 객체

| 객체/관계 | 구현계획 |
|---|---|
| POSMaster → CapabilityDefinition/Profile | 제품 정보와 기능별 지원 여부·방식·방향, 필요한 스키마/필드 매핑 작업 연결 |
| Store → StorePOSConnection | 현재 POS 1개를 참조하되 변경이력 보존. 접속 프로파일·점포식별·검증 단계·Capability별 테스트 결과 분리 |
| InterfaceProfile / StandardSchema / FieldCodeMapping / IntegrationRun | POS별 원천과 표준 모델 매핑, 전송/수신·오류·재처리 이력. 실제 비밀키나 DB 접속은 사용하지 않음 |
| Publication / Flyer / ExtractedProductCandidate | 점포·사업·상품/전단·게시기간·공개설정, 연동형/게시형/혼합형 출처 |
| PublishedSnapshot / PendingPublication / DeliveryAttempt | 마지막 성공 전송과 다음 반영 예정 데이터를 분리. 전송 실패가 현재 공개 스냅샷을 덮어쓰지 않게 설계 |
| ExcelTemplateVersion / ImportJob / SourceFile | 버전·필수열·파싱/검증결과·미리보기·대상 업무 참조, 파일 출처 및 제출 후 보존 |
| Attachment / AuditEvent / Notification / JobRun | 업무 ID별 증빙, 변경 전후/처리자/사유, 알림 정책과 처리할 일, 자동작업 결과 |
| Notice / CMSContent | 조직별 노출·대상·기간. 시스템 공지와 홈페이지 게시 목적을 구분 |

관계의 중심 흐름은 `조직/회원사/점포 + 사업참여 → 주차계획 → 예산/상품매핑 → 거래 → 청구 스냅샷 → AT 결과/불인정 → 소명/재심사 → 최종정산 → 협회입금/점포지급`이다. 공개 데이터는 참여점포의 운영정보와 공개 가능한 상품·전단에서 파생하며 전체 거래/상품 데이터를 그대로 공개하지 않는다.

### 6.4 PRD 표준 데이터 적용

PRD 17장의 `2026 농축산물 할인지원`, aT, 한국마트협회, 경기/강원지회, 한빛유통(주), 한빛마트 본점/강서점/마곡점을 공통 seed로 사용한다. 본점은 하이포스, 강서점은 부분연동, 마곡점은 비연동이라는 **시나리오를 개별 Capability 조합으로 표현**한다.

- 예시 32차: 2026-10-08~2026-10-14, 상품등록 마감 2026-10-07 00:00.
- 회차 예산: 100,000,000원, 기본 예비비 5,000,000원.
- 본점 정상확정, 강서점 예외확정 1건, 마곡점 등록중.
- 최초청구 4,720,000원 → 최종인정 4,620,000원 + 최종불인정 100,000원.
- 본점/강서점 공개 연동형, 마곡점 게시형.
- 마트 홈의 불인정 5건과 일괄소명 18건 장면은 서로 다른 범위/시나리오로 명확히 구성한다. 같은 필터의 합계가 서로 다르게 보이게 만들지 않는다.
- 여러 업무 시점을 보여야 하므로 과거 정산/지급 차수와 다가오는 상품등록 주차를 별도 seed로 준비한다. 추가 값은 목업 예시로 표시하고 PRD 공식값으로 취급하지 않는다.

## 7. 공통 상태값과 업무 라이프사이클

현재 코드에는 업무 상태값이 없으며 카운터의 숫자만 존재한다. 공통 상태 사전과 상태별 허용 액션/검증을 먼저 정의하고 모든 화면이 이를 사용해야 한다. 표시는 PRD 용어를 유지하되 내부 코드는 별도 상수로 관리하는 안을 제안한다.

### 7.1 PRD 명시 상태 목록

| 영역 | PRD 상태값 | 전이/제어 기준 |
|---|---|---|
| 사업 (6.1) | 준비 / 진행 / 일시중지 / 종료 / 보관 | 준비→진행→종료→보관; 진행/일시중지 전환. 종료 후 신규입력 차단·조회/이력 유지. 재개 세부정책은 미확정 |
| 계정 (6.2) | 승인대기 / 정상 / 정지 / 비활성 / 영구삭제 가능 | 승인/정지·복구/비활성 흐름. '영구삭제 가능'은 시스템 관리자 및 참조이력 부재 등 조건에 따른 자격으로 해석하며 모든 계정의 자동 종착상태로 만들지 않음 |
| 사업 참여 (6.3) | 미참여 / 신청작성중 / 신청완료 / 심사중 / 반려 / 참여예정 / 참여중 / 중지예정 / 중지 | 반려사유 후 재신청, 승인 후 효력시점 반영. 중지 후 과거이력 조회 유지 |
| 점포 POS 연동 (6.4) | 미설정 / 설정중 / 연결테스트 대기 / 연결성공 / 데이터검증중 / 정상연동 / 연동오류 / 연동중지 | 연결성공은 정상연동이 아님. 데이터/Capability 검증 후 활성화, 변경·오류 후 재검증 |
| 행사 주차 (6.5) | 계획수신/등록 → 협회 확인 → 예산배정중 → 행사상품 등록중 → 행사대기 → 집행중 → 집행종료 → 정산대상 → 정산진행중 → 최종정산완료 → 지급대기/지급중 → 완료 | 기본 순서를 유지. 정산/지급 단계는 연결 차수와 지급 결과를 참조해 요약 표시; 주차 화면에서 정산 원본을 별도 수정하지 않음 |
| 행사상품 등록 (6.6) | 데이터대기 / 가매핑 / 확인필요 / 검증오류 / 예외설정 / 정상확정 / 예외확정 / 마감미완료 | 단순 순차가 아닌 분기. 검증오류 수정→재검증 또는 허용 예외 설정→예외확정. 마감과 행사시작 재검증 필요 |
| 청구·검토 (6.7) | 청구예정 / 청구완료 / AT/정산 검토중 | 협회 청구확정 시 불변 스냅샷, 이후 결과/판정은 별도 기록 |
| 불인정·재심사 (6.7) | 마트 확인중 / 불인정 수용 / 이의신청 제출 / 협회 검토중 / AT 재심사중 / 최종 승인 / 최종 반려 / 최종 정산 완료 | 건별 소명·판정과 차수 전체 최종정산을 분리. 불인정 수용을 재심사 승인처럼 처리하지 않음 |
| 최종 지급 (6.8) | 최종정산 완료 → 정부지급 대기 → 협회 입금확인 → 점포 지급준비 → 지급중 → 부분실패 / 지급완료 | 관리자 승인/계좌검증 후 실행. 부분실패는 실패 점포만 재처리 |
| 미정 외부 연동 (6, 14) | 대기 / 수신 / 실패 / 수동처리 | 마지막 성공/실패·오류·다음 예정·재처리 이력과 함께 표현. 특정 기관 고유 상태코드는 발명하지 않음 |

PRD의 '최종정산완료', '최종 정산 완료', '최종정산 완료'는 주차/정산/지급 문맥별 표기다. 표시 사전에서 일관성을 정하되 객체별 상태를 하나의 전역 `status`로 합치지 않는다. 신청 반려 이력과 계정의 현재 상태도 구분한다.

### 7.2 농할 End-to-End 흐름과 차단 조건

| 단계 | 주요 주체/입력 | 상태 변화·결과 | 필수 차단/검증 |
|---|---|---|---|
| 1. 가입/참여 | 협회, 회원사, 점포 | 가입 승인 및 사업별 점포 참여 확정 | 미참여 점포 운영메뉴 차단; 사업/점포/Role 범위 검증 |
| 2. 원천 주차계획 | AT 직접등록 또는 Excel | 공식 계획 생성·원본 보존→협회 확인 | 목~수 주기, 기간 중복/동일 주차 중복 방지 |
| 3. 운영계획/예산 | 협회 또는 위임 지회 | 기한·총예산·배분/예비비 설정, 원장 기록 | AT 원천값과 운영값 분리, 범위/배분 합계 검증 |
| 4. POS 행사/상품 | 점포 + Capability별 수집 | 가매핑/확인→정상 또는 예외확정 | 매핑·상품명·필수품목·사진 검증; 예외 없는 미충족 확정 금지 |
| 5. 마감/행사시작 | 자동작업 모의 실행 | 행사대기/집행중, 예외 재검증 | 계획 미확정 점포 배정 0원 및 예비비 회수, 처리 이력/알림. 이 규칙과 상품 마감미완료의 연결 기준은 아래 미정 목록에 명시 |
| 6. 집행/사전 예방 | POS 수집 또는 파일 | 집행 집계·이상 감지·예비비 투입/회수 | 권한 없는 예산 변경 차단, 이상 감지와 공식 청구 데이터 구분 |
| 7. 청구 준비/상신 | 자동수집 또는 마트 Excel | 검증 통과 거래/제출본; 협회 최초청구 확정 | 검증 실패 거래 제외 및 사유 표시, 상신 후 제출본 재업로드로 덮어쓰기 금지 |
| 8. AT 검토 | 결과 Excel 또는 직접 판정 | AT 결과 원본→건별 불인정 | 원청구 보존, 같은 결과의 중복 반영 방지 및 버전 식별을 설계 |
| 9. 소명/재심사 | 마트→협회→AT | 건별 증빙/검토/최종 승인 또는 반려 | 일괄 소명 대상 목록/건수/제외 확인, 건별 판정 가능 |
| 10. 최종 정산 | AT 금액 확정 | 최종 스냅샷·정산공문, 최종 불인정 예산환원 | 재심사 중 금액은 보류, 최종 불인정 전 조기환원 금지 |
| 11. 협회 수령/점포 지급 | 협회 입금확인/승인 | 지급대상→이체파일→결과→완료 또는 부분실패 | 계좌검증 정상 필수, 지급ID 중복방지, 입금 즉시 자동송금 금지 |

사업 참여 중지는 알뜰소비 자율중지와 농할의 진행 회차/정산 의무 종료 후 효력을 구분한다. 가입 승인을 사업참여 승인과 동일 처리하지 않으며, 마트의 추가예산 요청 승인 흐름이나 별도 지급요청 흐름을 신설하지 않는다(PRD 10.8, 10.12).

### 7.3 기타 라이프사이클

- 회비: 기초값/실제입금 수신→후보 매칭→자동매칭 검토·수정 또는 수동지정→입금유형/메모·납부 반영. 구체 상태 이름은 PRD에 없으므로 후속 정의로 표시한다.
- 전단: 업로드→이미지 처리/OCR 모의결과→상품후보→마트 확인수정→기간 설정→게시→공개 전송 결과. 세부 상태 enum은 후속 정의하되 단계 자체를 생략하지 않는다.
- 공개: 공개설정 변경→다음 반영 예정→성공 전송 시 현재 공개 스냅샷 갱신; 실패 시 기존 성공 스냅샷 유지/재전송. 이는 현재/예정 비교 요구를 위한 구현 제안이다.
- Excel: 양식/버전 선택→파일 입력→파싱/검증→오류 행·미리보기→업무 반영→원본/결과 이력. 비연동 이상감지는 최신 분석결과 교체, 정산청구는 공식 증빙 보존이라는 차이를 유지한다.
- Soft Delete: 계정/조직 등의 비활성은 목록 기본숨김과 이력 보존으로 처리한다. 물리삭제는 참조이력 없는 제한 대상에 대한 시스템관리자 기능으로만 표현한다.

## 8. Role별 메뉴 및 데이터 접근 구조

### 8.1 접근권한 계산

PRD 4장의 공식을 그대로 설계 기준으로 사용한다.

`실제 접근권한 = 소속 조직 범위 + Role/조직 예외권한 + 참여 사업 + 사업-프로그램 매핑 + 점포 접근범위`

이는 권한을 단순 합산해 넓힌다는 뜻이 아니다. 각 조건을 함께 만족하는 메뉴·레코드·액션만 허용한다. 데이터 조회는 공통 범위 판정 함수를 사용하고, 액션 수행 시 현재 상태/위임권한/Capability까지 재확인한다. 상세 경로 직접 접근도 같은 검사를 거친다.

| Role | 데이터 범위 | 허용 업무 | 제외/제한 |
|---|---|---|---|
| 시스템 관리자 | 전체 | 플랫폼/조직/사업/권한/HUB/연동/감사, 계정복구. 보호 마스터 Role | 전역 접근을 정상 업무의 승인 주체와 혼동하지 않음. 불변 스냅샷 등 업무 제약 유지 |
| AT 사용자 | 해당 사업 전체 | 공식 계획, 감독 View, 청구 수신/검토, 불인정·재심사 최종판정, 최종금액/공문, 종합 통계 | 내부 이상 감지 제외, 협회→마트 지급실행 금지; 알뜰소비는 View만 |
| 협회 관리자 | 소속 운영조직 전체 | 회원/지회/심사/회비, 핵심정보 변경, 예산·농할 운영·청구·재심사 취합, 입금확인·지급, 공개/CMS | 다른 운영조직 접근 금지, AT 원천계획을 운영값으로 덮어쓰기 금지 |
| 지회 관리자 | 자기 지회 | 회원/회비/상품/정산/공개 조회, 허용 지회정보 수정, 위임받은 배분/예비비/회수 | 위임 없는 예산 액션 금지, 다른 지회 조회 금지, 정산 판정/지급실행 불가 |
| 마트 대표 관리자 | 자기 회원사 전체 점포 | 회원사 운영정보/점포/사업참여, 계정 승인·부관리자·점포권한, 상품확정/소명/공개 운영 | 공식 사업자정보/POS/지회 변경 금지, 추가예산 요청·지급요청 없음 |
| 마트 부관리자 | 자기 회원사 및 권한점포 | 대표가 위임한 가입승인·계정관리 및 허용 운영업무 | 대표와 동일 전권으로 가정하지 않음; 인원 상한·보호계정 세부조건은 TBD |
| 마트 일반 관리자 | 지정 권한점포 | Role과 점포권한으로 허용된 운영업무 | 회원사 전체 점포/계정관리를 자동 부여하지 않음 |

### 8.2 같은 상세의 역할별 액션

| 공통 상세 | 협회 | 지회 | 마트 | AT |
|---|---|---|---|---|
| 공식/운영 주차계획 | 원천 확인, 운영값·배분 | 조회, 위임 점포배분 | 행사상품 등 관련 화면에서 필요한 원천값·배정 조회 | 원천 등록/Excel |
| 점포→품목→거래 집행 | 전체 운영/허용 예산조정 | 자기 지회 조회/위임 조정 | 허용점포 조회 | 사업 감독 View |
| 최초 청구 상세 | 집계·확정·AT 전송/Excel | 조회 | 자동형 조회/비연동 제출 | 수신·검토 |
| 불인정 상세 | 취합·검토·AT 재심사 전달 | 조회 | 수용 또는 건별/일괄 소명·증빙 | 최종 승인/반려 |
| 최종정산·지급 상세 | 입금확인·승인·지급 | 조회 | 금액/지급일/계좌/상태 조회 | 금액 최종확정/공문, 지급실행 없음 |
| 공개/전단/연동 상세 | 소속조직 운영 | 자기 지회 조회 | 허용점포 운영/미리보기 | 사업 범위 조회, On/Off·수정·재전송 없음 |

- 참여하지 않은 사업도 **사업 참여 관리**에는 보여 안내/신청이 가능해야 한다. 운영메뉴 미노출과 신청경로 제거를 혼동하지 않는다.
- 중지/종료는 신규 운영을 차단하되 이력 조회를 남긴다. 혼합 참여 회원사는 선택 점포 집합에 따라 메뉴/상세 범위를 계산한다.
- Role 변경은 메뉴, 집계, 상세 및 액션에 즉시 반영하고 선택 중인 권한 밖 점포/상세는 해제하거나 접근불가로 안내하는 구현을 제안한다.
- 감사 전체 검색은 시스템 관리자 전용이다. 다른 역할의 자기 업무 원본/처리 이력 조회와 전역 감사 메뉴를 구분한다.
- 회원ID·전화번호·계좌 기본 마스킹과 파일 다운로드 이력을 공통 상세에 적용한다.
- 단일 HTML의 Role 전환/가드는 **시연용 권한 표현**이다. PRD 15.2의 서버측 권한검증·비밀값 암호화 저장은 향후 실제 서비스 요구로 남긴다. 이번 오프라인 구현에서 서버/실제 인증/실제 Secret을 도입하거나 클라이언트 가드를 보안 경계로 주장하지 않는다.

## 9. POS Capability 및 점포 POS 연동 구조

현재 POS 타입, 점포 연결정보, 표준 스키마, 매핑, 검증 단계는 전부 없다. POS 지정/Capability 정의/점포 실연동/업무 실행 가능 여부를 분리해서 신규 설계해야 한다.

### 9.1 Capability 모델과 화면 분기

| 기능군 | 필요한 옵션 | 사용하는 업무 |
|---|---|---|
| 기본 | 회원·점포·상품·가격 조회 | 마스터 조회, 점포/상품 식별 |
| 행사/계획 | 행사 조회·자동생성·수정, 농할상품 조회·등록수정, 예산 조회·입력수정 | 베이스 행사, 상품 수집/반영, 예산 반영 |
| 집행 | 판매실적, 거래상세, 취소/반품, 원거래 연결, 실시간/배치 | 집계, Drill-down, 취소 정합성, 누적 이상 감지 |
| 정산 | 정산용 자동수집, 회원식별, 할인/지원금, 정산 필수필드 | 자동청구 가능 여부, 검증/제외 사유 |
| 공개 | 일반 특매/행사 조회, 행사상품·행사가격, 알뜰소비 활용 | 유효한 농할/행사만 공개 |
| 방식/방향 | API/DB/파일/Excel, 단방향/양방향 | 입력/출력 경로, 폼/테스트/대체수단 |

지원 여부만으로 실행을 허용하지 않는다. **구현 제안:** `POS 제품이 지원하는 기능 ∩ 점포에서 설정·검증·활성화한 기능`을 실제 업무 가능 기능으로 계산하고, Role/참여/현재 상태 제약을 추가한다. '완전연동/부분연동/비연동'은 PRD 10.7의 사용자 흐름 설명이며 1/2/3 등급 enum으로 대체하지 않는다.

### 9.2 POS 마스터에서 점포 활성화까지

1. **POS 마스터:** 회사/제품/담당자/연락처/홈페이지/사용여부/비고와 Capability 옵션을 등록한다. 홈페이지 URL은 정보 표시용이며 외부 리소스 자동 로딩에 사용하지 않는다.
2. **데이터소스·인터페이스 프로파일:** 로컬/클라우드/파일형, 입출력 방식·방향 및 입력 항목 메타데이터를 정의한다. 실제 POS별 전문/필드 규격을 임의 작성하지 않는다.
3. **표준 스키마/매핑 작업:** 판매데이터 Capability를 켜면 점포코드·회원ID·거래ID/일시·상품코드/명·수량·정상가·자체할인·지원금·순결제·취소/원거래 등의 매핑 작업을 생성한다. 필수 여부와 실제 원천 필드명은 프로파일/상세기획으로 관리한다.
4. **점포 POS 지정/설정:** 제품 선택과 점포 연결 레코드를 분리한다. 선택만으로 '정상연동' 표시 금지.
5. **프로파일 기반 동적 폼:** 로컬은 매장코드·Host/IP·Port·DB/Instance·Agent·인증/허용정보, 클라우드는 점포/가맹점코드·Tenant·키 설정 여부 등 PRD 범용 항목을 사용한다. 목업에는 가짜값/마스킹만 둔다.
6. **검증 Wizard:** 연결테스트→점포식별→샘플데이터→스키마검증→Capability별 테스트→활성화. 성공/실패와 재시도 장면은 메모리 상태로 재현한다.
7. **운영/변경:** 현재상태·마지막 성공/오류·수집시각·변경 전후 이력. POS/접속정보 변경 경고, 재검증 전 기능 사용 제어.

마트는 사용 POS/연동상태 조회만 가능하다. 사용 POS 핵심정보 변경은 협회 관리자 요구(PRD 8.3, 10.3)를 반영하고, 시스템 관리자는 HUB에서 기술 프로파일/연결 설정을 관리한다. 협회의 기술 접속설정 세부 권한까지 자동으로 확대하지 않는다.

### 9.3 예산/행사 반영 전략

| 조건 | 계획 확정 이후 mock 흐름 | 불가/대기 상황 표시 |
|---|---|---|
| 행사 생성/쓰기 가능 | 상품 없는 베이스 행사 생성, 예산/할인율/개인한도 반영 | 생성/반영 실패, 재처리/수동대체 |
| 행사 조회/쓰기 가능 | 점포가 설정한 동일기간 행사 배치 확인→발견 시 배정예산 반영 | POS 행사 대기, 마지막 확인/다음 예정 |
| 쓰기 불가 | 확정 예산 수치와 POS 수동설정 안내 | 수동처리 경로 유지 |

POS 행사 매칭키는 **점포 + 행사 시작일 + 종료일**이다. 내부 이벤트 ID는 유지할 수 있지만 POS에 새로운 공통 매핑키를 추가하도록 요구하지 않는다(PRD 8.9).

### 9.4 Excel은 동등한 입력 경로

| 업무 | 연동 경로 | 파일/비연동 경로 | 공통 도착점 |
|---|---|---|---|
| AT 주차계획 | 시스템 입력/향후 API 모의수신 | 공식 Excel | OfficialPlan/EventWeek |
| 행사상품 | POS 수집+가매핑 | 직접입력/Excel | ProductMapping + 등록검증 |
| 이상 감지 | 회차 누적 수집·분석 | 최신 결과보고 Excel 일회 분석 | 조회는 공통, 분석자료 보존 정책은 구분 |
| 정산청구 | 자동수집·검증 통과 거래 | 결과보고 Excel→미리보기→상신 | 제출본/최초청구 스냅샷 |
| AT 결과/재심사 | 모의수신/시스템 판정 | 결과 Excel | 동일 불인정건/판정 이력 |
| 가중배분 | 화면 입력 | 배분 Excel | 동일 배분 검증/예산원장 |

시연용 파일 파싱/OCR/가매핑 결과는 로컬 샘플과 모의 상태로 구성할 수 있다. 업로드·검증오류·미리보기·반영·보존 단계는 실제로 조작 가능해야 하며 성공 토스트 하나로 대체하지 않는다. 입력 샘플/전단/증빙도 최종 HTML에 포함하여 인터넷이나 별도 샘플 파일 없이 시연할 수 있게 한다.

## 10. 구현 순서와 화면 간 의존성

순서는 **의존성을 해결하기 위한 단계**이며 뒷단 업무를 PRD 범위에서 제외하는 우선순위가 아니다. 각 단계 완료 시 데이터/상태/검증을 함께 구현하고, 빈 메뉴만 생성한 것을 기능 완료로 보지 않는다.

| 단계 | 구현 범위 | 선행 의존성 | 단계 완료 기준 |
|---|---|---|---|
| 0. 도메인/화면 계약 | 6~9절 객체·상태·권한·Capability 사전, PRD 19.1 화면 명세, TBD 목록 | 본 계획/PRD | 객체/ID/범위/상태 소유권 확정, 표준 seed 시나리오 정의 |
| 1. 앱 공통 기반 | P01의 셸, P02~P05, 공통 필터·테이블·상세·상태·파일 UI, 메모리 상태·감사 기반 | 단계 0 | Role/사업/조직/점포에 따라 메뉴·상세·액션이 일관되게 변경 |
| 2. 회원/점포/참여 | M01~M08, 계좌검증/회비/초기이관, 가입·사업참여 흐름 | 조직/계정/Role/사업 | 회원사와 점포 분리, 대표/일반 범위, 참여 효력/이력 시연 |
| 3. HUB/외부·파일 기반 | P06~P08, P09~P11의 화면, mock 입출력 어댑터 | 점포·권한·감사·파일 기반 | Capability 변경→스키마작업→점포연동 검증→정상/오류/수동경로 |
| 4. 원천계획/예산/상품 | N01~N04, 자동작업/알림과 연결 | 사업참여·POS 기능·Excel | AT 계획→협회/지회 배분→점포별 등록분기→검증/예외/마감/회수 |
| 5. 집행/이상 | N05~N06 | 확정 계획·상품·예산·표준 거래 | 범위별 합계와 상세 일치, 예비비/회수 원장 반영, 최신 Excel 분석 교체, AT 이상 메뉴 차단 |
| 6. 정산/재심사 | N07~N09 | 주차/차수·거래·첨부·파일·원장 | 제출/최초청구 불변, 결과 수신/Excel, 건별·일괄 소명, AT 최종판정, 보류/환원 |
| 7. 입금/지급 | N10 | 최종정산·계좌검증·권한·지급ID | 실제금융 없이 입금확인→관리자 승인→파일/결과→부분실패 재처리; 중복 지급 차단 |
| 8. 공개/전단 | C01~C05 | 단계 2~4의 점포 운영/참여/상품과 연동·파일 기반 | 연동형·게시형·혼합형, 현재/예정 미리보기, 실패/재전송, AT View |
| 9. 운영 완성 | M09~M11, C06, Role별 홈 완성, 알림·작업·감사 전체 연결 | 각 도메인에서 생성한 데이터 | 공지/CMS/가입 연결, 동일 데이터 기반 통계, 처리할 일 링크, 조직별 범위 |
| 10. 통합 시연 검증 | 표준 시나리오, 모든 Role/입력경로/오류/이력, 단일 HTML 검사 | 전 단계 | PRD 부록 C + 아래 인수조건 충족 |

알림/감사/스냅샷은 마지막에 한꺼번에 덧붙이지 않는다. 단계 1에서 기록 구조를 만들고 각 기능 구현 때 함께 기록하며, 단계 9에서 전체 화면 연결을 검증한다. 공개/전단은 의존 데이터가 마련되면 정산·지급 구현 완료를 기다리지 않고 진행할 수 있다.

### 10.1 주요 의존 경로

```text
조직/계정/Role ─┬─ 사업/프로그램 ─ 참여심사 ─ 점포 참여 ─┐
회원사/점포 ───┘                                      │
POS 마스터 ─ Capability ─ 스키마/매핑 ─ 점포연동 ──────┤
Excel 양식/파일 검증 ──────────────────────────────────┤
                                                      ▼
AT 원천계획 → 협회 운영계획/예산 → 지회·점포 배분 → 행사상품
                                                      │
                                                      ▼
집행 거래/이상 감지 → 청구 스냅샷 → AT 결과 → 소명/재심사
                                                      │
                                                      ▼
최종정산/예산환원 → 정부지급 대기 → 협회입금 → 승인/점포지급

점포 운영정보 + 사업참여 + 유효 행사상품/전단
    → 공개 예정 데이터 → 전송 결과 → 현재 공개 스냅샷/미리보기

모든 단계 → 업무 이력/감사/알림 → 역할별 홈/통계
```

### 10.2 표준 시연 및 인수조건

1. **권한/범위:** 같은 거래·청구를 협회/지회/마트/AT로 전환해 서로 허용 범위와 액션만 달라지는지 검증한다. 직접 hash 접근·Role 변경 직후에도 범위를 재검증한다.
2. **다조직·다사업:** 표준 한국마트협회 seed 외 최소 비교용 조직/사업 fixture를 제안한다. 이를 실제 기관 정책처럼 다루지 않고 범위 누수/하드코딩 방지 검증에만 사용한다.
3. **계획/등록:** PRD 32차 날짜·마감·예산, 본점/강서점/마곡점의 기능별 분기, 사진누락/상품명 오류/예외확정·재검증을 시연한다.
4. **예산/집행:** 배분 합계·예비비·회수·원장이 맞고, 마트 요청 승인 절차를 추가하지 않은 상태로 협회/위임 지회가 조정한다.
5. **청구/재심사:** 자동형과 Excel형이 동일 청구 구조로 수렴하고, 최초청구 4,720,000원이 재심사 후에도 보존된다. 최종인정 4,620,000원과 최종불인정 100,000원의 합계·환원 이력을 확인한다.
6. **일괄 소명:** 동일 상품+동일 사유 18건의 대상을 먼저 보여 일부 제외 후 적용하며, 개별 레코드와 개별 최종판정이 남는다.
7. **지급:** AT 확정만으로 지급 완료되지 않는다. 비정상 계좌 대상 생성 차단, 협회 입금확인·승인, 부분실패의 실패건만 재처리, 지급ID 중복 차단을 확인한다.
8. **공개:** 농할/현재 행사만 노출하며, 전단 후보 확인수정, 마지막 성공 화면과 다음 예정 화면의 차이, 실패/재전송을 확인한다. AT 운영버튼은 제공하지 않는다.
9. **파일/이력:** 정산 파일·결과·소명·최종정산 원본을 분리 보존한다. 일회성 이상분석 최신파일 교체와 공식 제출파일 보존이 혼동되지 않는다.
10. **전체 IA:** 5절 P/M/N/C 화면군과 Role별 메뉴를 대조하여 홈페이지/CMS, 회비/이관, 공통코드, 알림/작업/감사도 누락하지 않는다.
11. **배포:** 구현 변경 완료마다 `npm run build`, `npm run build:single`; dist는 HTML 1개. Windows Chrome/Edge file://에서 네트워크 offline, localStorage 차단 상태로 역할·메뉴·데이터·첨부 샘플·차트·상호작용을 확인한다.

추가 디렉터리는 역할이 명확할 때만 도입한다. Redux 등 운영 서비스 수준의 상태관리 라이브러리를 추가하지 않고 React Context/useReducer와 순수 함수로 시작한다. Role별로 독립 데이터를 만들면 동일 청구/판정이 서로 달라지므로 도메인별 공통 상태를 공유한다.

### 11.3 리팩터링 시 지킬 기술 경계

- 메뉴 표시, 데이터 selector, 액션 권한 검증에서 동일 access 정책을 사용한다. 목록을 숨기는 것만으로 상세 접근을 통제했다고 보지 않는다.
- 원장 계산·청구확정·재심사·지급승인을 JSX 이벤트 내부에 흩어놓지 않고 도메인 액션으로 관리한다. 복잡한 전역 프레임워크 대신 도메인별 모듈을 사용한다.
- 메모리 상태의 원본 스냅샷은 시연 세션 안에서 불변으로 보존한다. 새로고침 후 seed 초기화와 업무 중 원본 덮어쓰기를 구분한다. 영속성이 필요해도 localStorage 필수 의존은 금지한다.
- 정적 import를 기본으로 사용한다. 업무 페이지 lazy chunk, 런타임 CDN/웹폰트/API/외부 이미지 요청, Service Worker 서버 전제 등을 도입하지 않는다.
- 외부 입력/출력은 범용 mock 어댑터에서 표준 객체로 변환한다. 자동수신/수동등록/Excel/기초이관 출처를 보존한다.
- 업로드·다운로드는 브라우저 메모리와 로컬 파일 기능으로 구성할 수 있다. 기본 샘플은 HTML 내 포함하여 별도 파일을 갖고 있지 않아도 모든 시연 흐름을 실행할 수 있어야 한다.
- 스크립트 정적 검사는 현재 비정적 라이브러리 로더를 허용하므로 그것만으로 외부 요청 0을 증명하지 못한다. 후속 업무 추가 후 실제 오프라인 브라우저 검증을 계속 유지한다.
- 홈페이지는 이 단계의 관리자 목업 안에서 콘텐츠/가입 시나리오를 표현한다. 별도 인터넷 사이트나 실제 외부 서비스를 배포하지 않는다.
